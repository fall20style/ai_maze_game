## D-001. Python 단일 스택 + SDL 클라이언트

**배경** — 초기 계획(v0)은 브라우저(Vite + TypeScript + Canvas) 게임이었다. 그러나 학습·서빙·
평가가 모두 Python 이고, 데모의 핵심은 "서버가 권위를 갖는다"는 구조 검증이었다.

**선택지**

1. 브라우저 클라이언트 + FastAPI (초기안)
2. Python + pygame(SDL) 클라이언트 + FastAPI
3. 터미널/TUI 클라이언트

**결정** — 2안. 클라이언트도 Python 으로 두어 언어/빌드 도구를 하나로 줄였다.

**근거**

- JS 빌드 체인 없이 `python -m viewer.app` 한 줄로 실행.
- `SDL_VIDEODRIVER=dummy` 로 헤드리스 스냅샷이 가능해 CI/문서화가 쉽다.
- 학습 코드와 같은 좌표계/자료형을 쓸 수 있다(단, 클라이언트는 서버 코드를 import 하지 않음).

**결과** — `viewer/` 는 pygame 2.6.1 기반. 이후 R1(경로 탐색 0줄)을 문자열 스캔으로
검증하기 쉬워졌다. 관련: `dfe0ba6`, `968694c`.

## D-002. BERT-tiny + LoRA 정책

**배경** — "데이터가 없는 BERT에 미로 탐색 합성 데이터를 LoRA로 주입한다"는 것이 프로젝트의
출발 명제였다. 관측 벡터를 토큰처럼 취급해 BERT 에 통과시키는 구조가 필요했다.

**선택지**

1. BERT-tiny + LoRA (선형 투영 → BERT → action head)
2. BERT 전체 fine-tuning
3. 소형 Transformer/MLP 를 처음부터 학습
4. CNN/ResNet 기반 공간 정책

**결정** — 1안. `PolicyConfig(obs_dim=54, hidden=128, layers=2, heads=2)`.
LoRA 기본값은 `r=8` 이고, `checkpoints/wall` 학습에는 `r=32` 를 썼다(§7.1).

**근거**

- CPU 만으로 학습/추론 가능(당시 환경).
- LoRA 로 학습 가능 파라미터를 줄여 합성 데이터 규모(수만 샘플)에 맞춤.
- `PolicyConfig` 를 체크포인트에 함께 저장해 **관측 정의를 모델이 스스로 설명**하게 함.

**결과** — 왼손 법칙 증류는 성공(100%). 그러나 지식 지도 BFS 같은 공간 연산에는 표현력이
부족했다(D-007). 이 한계는 아키텍처 결정의 대가로 명시적으로 기록한다. 관련: `0198f03`.

## D-003. 관측 = 3×3 창 + 전역 방문 요약 (54차원)

**배경** — 초기 관측은 3×3 창 + 위치/목표/직전 행동 등 **29차원**이었다. 롤아웃에서 같은
구역을 무한히 맴도는 실패가 반복됐다(실측 루프율 87%).

**선택지**

1. 29차원 유지 (3×3 창만)
2. 전역 방문 요약 5×5 추가 → 54차원
3. 창을 5×5/7×7 로 확대
4. 전체 미로 격자를 관측에 포함

**결정** — 2안. 미로를 5×5 블록으로 나눈 **방문 여부**만 추가했다.

**근거**

- "이 구역을 이미 지나왔다"는 정보가 국소 창에는 없다.
- 전역 요약은 에이전트 자신의 이동 기록이므로 **정답 미로를 알려주지 않는다**. 길찾기 지능은
  여전히 신경망 안에 남는다.
- 4안(전체 미로)은 학습 목표를 trivial 하게 만들고 "부분 관측" 실험을 무너뜨린다.

**결과** — 루프율 87.1% → 74.7% 로 감소. 다만 성공률은 30.0% → 27.5% 로 개선되지 않았다.
전역 요약만으로는 부족하다는 것이 다음 결정(D-004)의 출발점이다. 관련: `0198f03`.

## D-004. BFS 최단 라벨 폐기 — "식별 불가능" 진단

**배경** — 초기 데이터 라벨은 **전체 미로를 아는 BFS 최단 경로의 다음 행동**이었다.
단일 스텝 val acc 는 76~88% 였지만 롤아웃 성공률은 17~38% 에 그쳤다. DAgger 를 적용해도
17.5% 로 악화됐다.

**관찰**

- 9×9 seed=101 에서 `(3,2) ↔ (3,3)` 2-cycle. 전역 방문 합이 2에서 늘지 않는다.
- 모델은 "목표 방향으로 직진"하는 근시안 정책을 학습하고, 벽/막다른 길에서 진동한다.

**선택지**

1. 모델/데이터를 더 키운다
2. DAgger 를 더 돌린다
3. 라벨을 **관측만으로 계산 가능한 전문가**로 교체한다
4. 관측에 전체 미로를 넣는다

**결정** — 3안. BFS 최단 라벨은 학습에서 폐기하고, 평가 지표(최단 경로 대비 비율)로만 남긴다.
4안은 프로젝트 명제를 포기하는 것이므로 배제.

**근거** — BFS 최단 행동은 전체 미로를 아는 전문가의 라벨이다. 3×3 창 + 압축 방문 요약만
가진 정책에게 이 라벨은 **관측으로 결정되지 않는다(unidentifiable)**. 함수 근사 실패가 아니라
목표 자체가 부분 관측의 함수가 아니었다.

**결과** — 라벨 교체(D-005)로 성공률 27.5% → 100%. "정확도가 낮다"가 아니라 "학습 목표가
잘못 정의됐다"는 진단이 맞았다. 관련: `decb460`.

## D-005. 왼손 법칙(wall follower) 전문가 라벨

**배경** — 관측만으로 결정되는 전문가가 필요했다.

**선택지**

1. 왼손 법칙 (왼쪽 → 직진 → 오른쪽 → 뒤)
2. 방문 격자 기반 DFS
3. 랜덤 정책
4. 사람 플레이 로그

**결정** — 1안. `wall_follow_action(maze, pos, heading)`.

**근거**

- 현재 3×3 창 + `last_action` 두 정보만으로 결정된다 → **관측의 함수**.
- 완벽 미로(트리)에서는 목표 도달을 보장한다.
- 결정론적이라 데이터 라벨이 안정적이고, 테스트로 100% 도달을 검증할 수 있다.

**결과**

- `data/wall`: 46,142 train 샘플, val acc **1.0000**, 롤아웃 **100%** (9~15, 15×15, 17·19 모두).
- 벽 충돌 0. optimality 2.28~4.84 (비효율은 정상 동작).
- 학습하지 않은 크기에서도 100% → 정책이 크기가 아니라 **국소 규칙**을 학습했다.

관련: `decb460`, `2a85fe5`.

## D-006. BFS 솔버는 평가 전용, 지연 import

**배경** — R1 은 "프론트엔드에 경로 탐색 코드가 없다"이다. 그런데 서버에는 BFS 가 필요하다
(최단 경로 지표, 미로 검증, frontier 전문가). 경계를 어디에 그을 것인가?

**선택지**

1. 솔버를 서버 API 코드에서도 자유롭게 사용
2. 솔버를 학습/평가 디렉터리로 완전히 이동
3. `app/game/solver.py` 에 두되 **API 경로에서 호출 금지**, `app/game/__init__` 에서 지연 import

**결정** — 3안.

**근거**

- 미로 생성(`randomize_endpoints`)이 내부적으로 BFS 최장 거리를 계산해야 한다. 완전 분리는
  순환 import 를 만든다.
- 클라이언트가 `import app.game` 을 하더라도 solver 가 메모리에 올라오지 않게 하면,
  "클라이언트 프로세스에 경로 탐색이 없다"를 런타임으로도 보장할 수 있다.
- API 코드(`app/api/*`)는 solver 를 import 하지 않는다.

**결과** — `tests/test_viewer.py::test_game_package_does_not_eagerly_import_solver` 와
`test_client.py` 의 subprocess import 검사로 고정. 관련: `35f3d75`, `9dea84c`.

## D-007. 지식 지도(belief map) + frontier 전문가

**배경** — "규칙을 그냥 쓰면 되지 않나?"라는 질문이 남았다. 왼손 법칙은 20줄짜리 함수이고,
학습 모델은 그 규칙을 그대로 증류했을 뿐이다(D-005). 학습이 규칙을 이기려면 **더 나은 전문가**가
필요하고, 그 전문가의 라벨도 관측의 함수여야 한다.

**선택지**

1. 창을 키운다 (5×5/7×7)
2. 순환 메모리(RNN)를 추가한다
3. 관측에 **누적 지식 지도**를 추가하고, 그 위에서 BFS 하는 frontier 전문가를 만든다
4. 전체 미로를 관측에 넣는다

**결정** — 3안. `known_wall`/`known_floor` 두 채널(`map_size × map_size`)을 추가하고,
`frontier_action(known, pos, goal)` 을 교사로 사용.

**전문가 규칙**

1. 목표를 이미 봤으면 → 지식 지도 위 최단 경로의 첫 스텝
2. 아직 못 봤으면 → 미탐색 경계 중 `거리 + 0.6 × 목표까지 맨해튼` 최소 칸으로

**근거**

- 지식 지도는 **에이전트가 직접 본 셀만** 누적한다. 정답 미로가 아니다.
- 라벨이 관측으로 완전히 재현됨을 테스트로 확인:
  `test_frontier_labels_are_a_function_of_the_observation`.
- 지식 지도가 전체 미로를 포함하지 않음도 확인:
  `test_frontier_belief_never_contains_the_full_maze`.
- frontier 교사는 왼손 법칙보다 빠르다: test split 24 미로에서 1.868 vs 2.145.

**결과 — 학습은 실패**

| 런 | 데이터 | val acc | 롤아웃 성공률 |
|---|---|---|---|
| `frontier` (BC) | 36,436 샘플 / 479차원 | 92.62% | **62.5%** |
| `frontier_d` (DAgger) | +45,803 온폴리시 샘플 | 92.87% | **37.5%** |

라벨은 재현 가능한데도 학습이 실패했다. 원인은 **표현력**이다. `Linear(479→128)` 한 층 +
2-layer BERT-tiny 로는 225칸 지식 지도 위 BFS 를 계산할 수 없다. 공간 연산에는 가중치 공유
(convolution)라는 inductive bias 가 필요한데 현재 구조에는 없다. DAgger 악화도 같은 이유로
설명된다. 관련: `43a5643`, `31a1647`.

## D-008. optimality ≤1.3 목표 폐기 — 정보 한계

**배경** — 초기 목표는 "최단 경로 대비 1.3배 이내"였다.

**측정**

- 120 미로 실측 상한: frontier **1.794**, 왼손 법칙 **1.896**.
- `goal_weight` 를 0.0~4.0 으로 바꿔도 1.789~2.039 로 거의 평평.

**결정** — 1.3 목표를 폐기하고, **정보 한계**로 설명한다.

**근거** — 미로를 모르는 정책은 최단 경로를 걸을 수 없다. 탐색 비용이 반드시 붙는다.
관측 가능한 최선의 전문가도 1.79 근처다. 1.3 은 튜닝 부족이 아니라 **원리적으로 불가능**하다.

**결과** — README/PLAN 의 목표 지표를 "성공률 + optimality(참고)"로 바꿨다. 이후 벤치마크는
1.85~1.87 수준을 정상 범위로 본다. 관련: `31a1647`.

## D-009. 서버 권위 분리 (R1~R4)

**배경** — W2.5 의 뷰어는 로컬에서 `HumanBrain`/`PolicyBrain` 을 직접 돌렸다. 즉 클라이언트
프로세스에 모델과 이동 결정이 있었다. "서버가 권위를 갖는다"는 요구를 만족하려면 구조를
바꿔야 했다.

**선택지**

1. 뷰어 안에 brain 을 유지하고, 서버는 기록만 저장
2. 서버가 모든 판단을 하고 클라이언트는 HTTP 로 상태만 받는다
3. 하이브리드(사람은 로컬, AI는 서버)

**결정** — 2안. `app/api` 가 미로·환경·brain·벽/승리 판정을 모두 소유한다.

**근거**

- R1: 클라이언트에서 경로 탐색 코드를 완전히 제거.

## D-018. 미사용 `word_embeddings` 프루닝

**배경** — 학습된 LoRA-BERT 체크포인트가 18.2 MB 인데, 그중 15.6 MB 가 30,522×128
어휘 임베딩이다. `BertPolicy.forward` 는 항상 `inputs_embeds` 를 넘기므로 HF
`BertEmbeddings` 는 `word_embeddings` 를 호출하지 않는다.

**선택지**

1. 그대로 둔다 (호환성 최대)
2. 체크포인트 저장 시 `word_embeddings` 키만 제거
3. **1행 0 임베딩으로 교체하고 config 에 플래그를 저장**
4. int8 양자화로 추가 압축

**결정** — 3안. 4안은 이 환경에서 보류.

**근거**

- 2안은 `load_state_dict` 가 키 누락으로 실패한다. 모델 구조와 state_dict 모양이 일치해야 한다.
- 3안은 `PolicyConfig.prune_word_embeddings` 를 저장해 `BertPolicy.load` 가 가중치를 읽기
  **전에** 같은 모양을 만들게 한다. 별도 인자 없이 로드되고, 일반 체크포인트는 영향이 없다.
- `position_embeddings`/`token_type_embeddings` 는 `inputs_embeds` 경로에서도 더해지므로 유지.
- int8: torch 2.14.1+cpu 가 `onednn` 엔진만 지원해 `quantized::linear` 추론이 실패했고,
  dynamic int8 은 2.9ms → 4.9ms 로 오히려 느려졌다. 이번 범위에서 제외.

**결과** — 파일 18,221,863 B → 2,595,367 B (−85.8%). 로짓 최대차 0.0(`torch.equal`).
같은 60 미로 롤아웃에서 성공률 100%, 평균 스텝 96.9, 짝지음 Δ 0.0. 상세: [PRUNE.md](./PRUNE.md).

## 부록. 되돌아보기 — 가장 큰 판단 착오

1. **"정확도가 낮으니 모델을 키우자"** — 실제 원인은 라벨이 관측의 함수가 아니었던 것.
   모델 크기보다 **문제 정의**를 먼저 의심해야 했다(D-004).
2. **"더 강한 교사를 쓰면 학습이 따라온다"** — frontier 라벨은 재현 가능했지만, 아키텍처가
   공간 연산을 표현하지 못했다(D-007). 라벨과 표현력은 별개 문제다.
3. **"AI가 규칙을 이길 것"** — 증류는 규칙을 이기지 못한다. 규칙을 이기려면 규칙과 다른
   inductive bias(conv)가 필요하다(D-013).
4. **"클라이언트에 brain 을 두면 편하다"** — R1~R4 를 만족하려면 권위를 서버로 옮겨야 했다.
   편의성보다 불변 규칙이 우선(D-009).

이 네 가지가 이후 설계(서버 권위, 관측 계약, 규칙 우선, 문서 분리)의 직접적인 근거다.
